# `@noob-naive-ui/i18n`

The dependency foundation of the workspace (`src/index.ts` exports the whole
surface). It implements a **component-first, locale-first message contract**: each
library component ships a locale-first JSON resource
(`src/locales/<ComponentName>.json`), and hosts override individual message leaves
through an app-scoped plugin snapshot without ever touching the host global
Composer's registry.

Depends only on `vue`, `vue-i18n`, `zod`, and `tsafe` (for `objectEntries`).
Consumed by `@noob-naive-ui/admin`, `@noob-naive-ui/ui`,
`@noob-naive-ui/admin-vue-router` (for the persisted `I18nText` tab label), and
mirrored standalone by `@noob-naive-ui/prototype-i18n-verification`.

## Modules and responsibilities

### `i18n-text.ts` — `I18nText` and `resolveI18nText`

`I18nText` is a Zod discriminated union (`i18nTextSchema`):

```ts
type I18nText =
  | { kind: "string"; value: string }        // verbatim display text
  | { kind: "i18n"; key: string; named?: Record<string, string | number | boolean> };
```

- `i18n` values are resolved against the host global Composer **at render time**,
  so they stay reactive to locale switches and survive history-state persistence
  as their message key (admin-vue-router persists tab labels through this schema).
- `named` interpolation values must be JSON-serializable primitives because they
  are persisted with history state (enforced by the schema).
- `resolveI18nText(text, translate)` resolves an `i18n` value via the passed
  translator (e.g. `composer.t`) or returns the `string` value verbatim.

Focused tests: `tests/i18n-text.test.ts` — accepts each kind, rejects unknown
kinds and non-primitive `named` values, and proves resolution behavior.

### `library-i18n-plugin.ts` — `createLibraryI18nPlugin`

A factory that produces the complete plugin descriptor for one component library:

```ts
type LibraryI18nPlugin<LocaleName, Locale> = {
  plugin: (app, options?) => void;            // provides the override snapshot
  overridesKey: InjectionKey<...>;            // typed app-scoped snapshot key
  emptySnapshot: Readonly<{ messages: {} }>;  // frozen; absent-plugin fallback
  selectComponentOverrides: (messages, componentId) => per-locale slice;
};
```

- Override tree type `LibraryI18nOverrides<LocaleName, Locale>` is a
  locale-first, per-component, deeply-optional partial tree
  (`Partial<Record<Locale, DeepPartial<Locale>>>`).
- The plugin **never creates an i18n instance and never registers global
  messages**; locale and fallback-locale authority stay with the host global
  Composer. Caller options are defensively copied with `structuredClone` at
  installation, so mutating the caller's objects after `app.use` cannot affect
  current or future mounts.
- `selectComponentOverrides` returns only the locales that actually carry a slice
  for the requested component, so absent locale keys never yield undefined
  override entries.
- The factory exists so plugin transport, empty snapshot, and slice selection are
  derivable from the message schema and need no per-package implementations.

Focused tests: `tests/library-i18n-plugin.test.ts` — frozen empty snapshot,
per-locale slice selection, defensive copying, empty-component-schema support.

### `use-component-i18n.ts` — `createComponentI18n` / `getComponentI18n`

The per-component Vue I18n registry:

- `createComponentI18n({ messages, plugin, componentId })` creates a **fresh
  local Composer** (`useScope: "local"`, `inheritLocale: true`) that inherits the
  root locale and fallback locale, seeds packaged defaults first and the
  component's plugin override slice second (overrides win at the leaf), then
  provides it to descendants. Each call builds a NEW Composer; it is not
  idempotent.
- With `__root && inheritLocale`, Vue I18n 11.4.8 initializes fallback settings
  from the root Composer; the code then sets `composer.fallbackRoot = true` so
  keys absent from the package registry — notably host-authored tab labels and
  other host-global messages — resolve through the same local Composer.
- Absent plugin installation, `inject(plugin.overridesKey, plugin.emptySnapshot)`
  yields the frozen empty snapshot, so packaged defaults always render.
- `getComponentI18n()` resolves the nearest ancestor component Composer and
  throws outside a `createComponentI18n` provider (fail-fast, mirroring
  `useAdminShell`). The injection key `componentI18nKey` is **module-private** —
  descendants reach the composer only through `getComponentI18n`.

Focused tests: `tests/use-component-i18n.test.tsx` (happy-dom) — defaults
without the plugin, override-merge with sibling survival, `fallbackRoot` kept
true, host-authored key resolution, locale-ref following the root locale, nearest
ancestor resolution, and the no-ancestor throw.

### `use-global-i18n-sync.ts` — `useGlobalI18nSync`

One-way synchronization of a reactive locale source (ref/computed/getter) into the
host's single global Composer:

```ts
useGlobalI18nSync(() => preferences.locale); // immediate by default
```

- Intended for store-owned locale authorities: the store remains the source of
  truth and the global Composer (and every inheriting local Composer) follows.
- `immediate` defaults to `true` so the current value is authoritative at setup.
- The host seeds the Composer at creation for pre-shell screens (login page); this
  composable covers everything after the shell mounts.

Focused tests: `tests/use-global-i18n-sync.test.tsx` — immediate push, one-way
propagation, deferred initial write.

## The locale-first resource contract

Every translating library component owns a file `src/locales/<ComponentName>.json`
whose top level is keyed by locale (`en`, `zh-CN`, …). The admin package uses
`src/locales/AdminShell.json` and `src/locales/AdminLoginPage.json`; see
[Admin i18n](admin/i18n.md). Message-shape types are generated from
these files by `tooling/vite/json-locale-types` (see
[Tooling — Vite plugins](../tooling/vite-plugins.md)), so packaged messages and
the public override contract cannot drift.

## Change surface for package authors

To add a translating component to a library package:

1. Create `src/locales/<ComponentName>.json` (locale-first) in that package.
2. Add the component id to the package's `ComponentId` union and the derived
   `Locale` schema (admin: `src/i18n/admin-locale.ts`).
3. In the component, call `createComponentI18n({ messages, plugin, componentId })`
   and read text through the returned composer `t`; descendants use
   `getComponentI18n()`.
4. Let `createJsonLocaleTypesPlugin` (package build) or the watcher plugin (app
   dev server) regenerate the committed `locale-types.generated.ts`.
5. The narrowest validation is that package's vitest suite (e.g. admin's
   `tests/i18n-contract.test.tsx` proves override snapshotting and zh-CN defaults).
