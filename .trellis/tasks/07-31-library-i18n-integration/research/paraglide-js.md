# Paraglide JS: Capability Assessment for Library i18n

**Research date:** 2026-07-31
**Scope:** Can reusable Vue component libraries (`@noob-naive-ui/ui`, `@noob-naive-ui/admin`) ship compiled default translations via Paraglide JS and let a consuming host override specific messages without forking source?

## Executive Summary

**Paraglide JS is architecturally incompatible with the "library ships defaults, host overrides at runtime" pattern.** The compiler-first design statically bakes messages into ESM functions at build time. There is no runtime message registration, merging, or override API. Three workarounds exist but none fully satisfy the PRD's requirements. Paraglide JS is best suited for applications that own their entire message catalog; it is not designed for reusable component libraries that ship translations independently.

---

## 1. Compile-Time Architecture

Paraglide JS is a **compiler-first** i18n library. It does not load or resolve messages at runtime. Instead:

1. Messages are authored in `messages/{locale}.json` files (or any format via plugins) [1].
2. The compiler (`paraglide-js compile`) reads these files and generates **one ESM function per message** in `./paraglide/messages.js` [1].
3. Application code imports and calls these functions like any other JavaScript function: `m.greeting({ name: "World" })` [2].
4. The bundler tree-shakes unused message functions, eliminating dead translations from the final bundle [1].

**This means message content is fully determined at compile time.** There is no runtime dictionary, no message loading, and no API to register, replace, or merge messages after compilation.

**Sources:**
- [1] Paraglide JS Architecture: https://paraglidejs.com/architecture — "Paraglide is a compiler-based i18n library. It compiles your translation files into JavaScript functions."
- [2] Paraglide JS Basics: https://paraglidejs.com/basics — shows `m.greeting({ name: "Samuel" })` usage.

## 2. Message IDs

Paraglide uses flat keys that become JavaScript identifiers. The recommended convention is **random human-readable keys** like `calm_green_otter` (generated by the Sherlock IDE extension) rather than semantic keys like `login_button_label` [3].

Key properties relevant to library distribution:
- Keys are globally unique within a single `project.inlang` compilation.
- There is **no namespace mechanism** built into the compiler — all keys share one flat namespace.
- Nested keys (e.g., `nav.home`) are supported via bracket notation `m["nav.home"]()` but compile to the same flat function namespace [3].
- **No key prefixing or scoping** is available to isolate library messages from host messages within a shared compilation.

**Sources:**
- [3] Paraglide JS Message Keys: https://paraglidejs.com/message-keys — covers flat vs nested keys, random ID recommendation.

## 3. Project/Inlang Settings Ownership

Every Paraglide compilation requires a `project.inlang/settings.json` that defines:

- `baseLocale` — the default locale
- `locales` — the list of supported locales
- `modules` — plugins (e.g., message format plugin)
- `plugin.inlang.messageFormat.pathPattern` — where message files live [4]

**Key constraint:** A `project.inlang` directory is owned by exactly one entity that controls its settings, locales, and message files. In a monorepo, the documented patterns are:

- **Pattern 1 (recommended):** One shared `project.inlang` at the monorepo root; each consuming package compiles separately from it with its own strategy options [5].
- **Pattern 2:** A dedicated shared i18n package that compiles once; all consumers import from it — but they must all use the same locale detection strategy [5].

**Neither pattern allows a library to ship its own `project.inlang` independent of the host.** If a library ships a `project.inlang`, the host must either compile it as part of the host's build (Pattern 1) or import pre-compiled output from a shared package (Pattern 2). There is no "library owns project.inlang, host extends it" model.

**Sources:**
- [4] Inlang Message Format Plugin: https://inlang.com/m/reootnfj/plugin-inlang-messageFormat — shows `project.inlang/settings.json` structure.
- [5] Paraglide JS Monorepo Setup: https://paraglidejs.com/monorepo — documents both shared-project and shared-package patterns.

## 4. Runtime APIs

The generated `runtime.js` exports:

| Export | Purpose |
|---|---|
| `getLocale()` | Returns the current locale |
| `setLocale(locale, opts?)` | Sets locale (triggers full document navigation by default) |
| `locales` | Array of configured locales |
| `baseLocale` | The base locale string |
| `localizeHref()` | Generates localized URLs |
| `overwriteGetLocale(fn)` | Replaces the locale getter |
| `overwriteSetLocale(fn)` | Replaces the locale setter |
| `defineCustomClientStrategy(name, handler)` | Defines a custom locale strategy |
| `defineCustomServerStrategy(name, handler)` | Defines a server-side custom strategy |

**Critical finding:** `overwriteGetLocale` and `overwriteSetLocale` control **locale resolution only** — which language is active. They do **not** affect message content. There is no `overwriteMessages()`, `mergeMessages()`, `extendMessages()`, or any API to modify what `m.greeting()` returns [6].

The runtime also provides `AsyncLocalStorage`-based request isolation for SSR via `paraglideMiddleware()` [7].

**Sources:**
- [6] Paraglide JS Runtime API: https://paraglidejs.com/runtime — documents all runtime exports.
- [7] Paraglide JS SSR: https://paraglidejs.com/server-side-rendering — documents `paraglideMiddleware` and `AsyncLocalStorage`.

## 5. Message Compilation Output

The compiler generates one of two output structures controlled by `outputStructure` [8]:

### `message-modules` (default)
```
paraglide/
  messages/
    hello_world/
      index.js   # imports locale-specific module based on getLocale()
      en.js      # export const hello_world = () => "Hello World!"
      de.js      # export const hello_world = () => "Hallo Welt!"
  messages.js     # re-exports all message functions
  runtime.js      # locale management
```

### `locale-modules`
```
paraglide/
  messages/
    en.js         # all English messages in one module
    de.js         # all German messages in one module
  messages.js
  runtime.js
```

In both structures, **message text is a string literal inside a compiled function.** There is no runtime indirection or lookup table that could be patched. The generated code looks approximately like:

```js
// en.js (compiled)
export const greeting = (inputs) => `Hello ${inputs.name}!`;
```

**Sources:**
- [8] Paraglide JS Compiler Options: https://paraglidejs.com/compiler-options — documents `outputStructure`.

## 6. Dynamic Messages

Paraglide supports dynamic message selection, but it works by **pre-declaring** which messages are used [2]:

```js
const messages = {
  greeting: m.greeting,
  goodbye: m.goodbye,
};
messages["greeting"](); // "Hello World!"
```

This is for runtime key selection, not runtime message content. The content of `m.greeting` is still baked in at compile time. **There is no way to supply a translation string at runtime** that the message function would use.

**Sources:**
- [2] Paraglide JS Basics: https://paraglidejs.com/basics — "Specify messages beforehand to preserve tree-shaking."

## 7. Library/Package Distribution

The officially documented approach for shared UI packages is [5]:

### Option A: Pass translated strings as props (recommended simplest)

```tsx
// packages/ui (no Paraglide dependency)
export function SaveButton(props: { label: string }) {
  return <button>{props.label}</button>;
}

// packages/web (host app)
import * as m from "./paraglide/messages.js";
<SaveButton label={m.save()} />;
```

**Assessment:** This works but requires every translatable string in the library to be passed as a prop. It does not satisfy the PRD requirement of "zero defaults boilerplate" — the host must explicitly pass every message.

### Option B: Separate compilation with locale forwarding

```tsx
// packages/ui compiles with --strategy baseLocale
// packages/ui/src/i18n.ts
import { overwriteGetLocale, overwriteSetLocale } from "./paraglide/runtime.js";

export function initUiI18n(options: {
  getLocale: () => Locale;
  setLocale: (locale: Locale) => void;
}) {
  overwriteGetLocale(options.getLocale);
  overwriteSetLocale(options.setLocale);
}

// packages/web/src/main.ts
import { getLocale, setLocale } from "./paraglide/runtime.js";
import { initUiI18n } from "@myorg/ui/i18n";
initUiI18n({ getLocale, setLocale });
```

**Assessment:** This lets the UI library follow the host's locale, but the library's messages are still its own compiled defaults. **There is no host override of individual library messages.** The `initUiI18n` call only shares locale state, not message content.

### Option C: Shared i18n package (single compilation)

All messages (host + library) live in one `project.inlang` and compile once. All consumers import from the shared package.

**Assessment:** This collapses library/host boundaries into a single message catalog. The host could edit library message files directly, but this is source forking, not runtime override. It also forces all consumers to use the same locale strategy.

**Sources:**
- [5] Paraglide JS Monorepo Setup: https://paraglidejs.com/monorepo — documents all three patterns.

## 8. Tree-Shaking Implications

Tree-shaking is a core Paraglide feature: unused message functions are eliminated by the bundler [1]. For a library shipping default translations, this creates a tension:

- If the library ships compiled messages but the host only imports a subset, unused library messages are **tree-shaken out** — they never reach the browser.
- If the host needs to override a message, the original library message must still be imported (otherwise there's nothing to override), but Paraglide's architecture makes this impossible: messages are functions, not data.

**There is no "ship all, override some" mechanism.** The compilation model means messages are either imported and used as-is, or tree-shaken and absent.

**Sources:**
- [1] Paraglide JS Homepage: https://paraglidejs.com — "Messages compile to ESM functions, so unused translations are eliminated by your bundler."

## 9. Locale Switching

`setLocale()` triggers a **full document navigation** by default (navigates to localized URL or reloads) [2]. This is fundamentally different from Vue I18n's reactive `locale` change:

- Vue I18n: Changing `locale` reactively updates all `$t()` calls in-place.
- Paraglide: Changing locale reloads the document; the new document renders with the new locale's compiled message functions.

The `setLocale(locale, { reload: false })` escape hatch exists but is explicitly documented as **not for normal locale pickers** — it does not update document state, framework state, or URL [2].

**Implication for the PRD's architecture:** The PRD assumes a single reactive Vue I18n Composer whose locale switch instantly updates all components. Paraglide's full-navigation model is incompatible with this expectation unless a complete re-architecture to per-locale document loads is acceptable.

**Sources:**
- [2] Paraglide JS Basics: https://paraglidejs.com/basics — "Locale switching uses a full document navigation."

## 10. Vue Integration

Paraglide JS is framework-agnostic. The generated message functions work in any JS framework. A Vue-specific adapter exists:

- `@inlang/paraglide-js-vue` (v1.0.2, ~757 weekly downloads) [9]
- Provides `<ParaglideMessage>` component for rendering messages with rich-text markup [10]
- Does **not** provide a Vue I18n-like composable, plugin, or reactive locale system
- Does **not** provide message merging, override, or registration APIs

The adapter is a thin markup-rendering wrapper, not a full Vue I18n integration. It does not change any of the architectural constraints described above.

**Sources:**
- [9] @inlang/paraglide-js-vue on npm: https://www.npmjs.com/package/@inlang/paraglide-js-vue
- [10] Paraglide JS Markup (Vue example): https://paraglidejs.com/markup — shows `<ParaglideMessage>` with `h()` render functions.

## 11. SSR / Multi-App Implications

Paraglide's SSR uses `AsyncLocalStorage` for request isolation [7]. The documented approach for shared UI libraries in SSR:

> "In SSR apps, request safety still comes from the app runtime. Inject the app's request-scoped `getLocale` function instead of storing a concrete locale globally in the UI package." [5]

This is the same `initUiI18n` pattern from Option B above — locale forwarding, not message override.

For **multiple Vue applications** on the same page, each Paraglide compilation produces its own `runtime.js` with independent locale state. Locale state is not shared between separate compilations. The documented solution is `overwriteGetLocale`/`overwriteSetLocale` to point one runtime at another's locale state [5].

**Sources:**
- [5] Paraglide JS Monorepo Setup: https://paraglidejs.com/monorepo
- [7] Paraglide JS SSR: https://paraglidejs.com/server-side-rendering

## 12. Any Documented Override/Extension Mechanism?

### Compile-time only: Message Format Plugin pathPattern merge

The inlang message format plugin supports **multiple `pathPattern` values** that are merged at compile time, with later files overriding earlier ones for identical keys [4]:

```json
{
  "plugin.inlang.messageFormat": {
    "pathPattern": [
      "./defaults/{locale}.json",
      "./overrides/{locale}.json"
    ]
  }
}
```

**This is a compile-time merge, not runtime.** The override happens when `paraglide-js compile` runs, before any code is shipped. It is designed for splitting a single project's messages across files (e.g., shared base + domain-specific overrides within the same organization), not for a library to ship defaults that an independent host overrides at runtime.

**Sources:**
- [4] Inlang Message Format Plugin: https://inlang.com/m/reootnfj/plugin-inlang-messageFormat — "Messages from all matching files will be merged... value from the last file in the array will override earlier ones."

### No runtime override API exists

After an exhaustive search of the official documentation, GitHub source, issues, and npm registry, **no runtime message override API exists in Paraglide JS.** The following were specifically sought and not found:

- `mergeMessages()`, `extendMessages()`, `overrideMessages()`, `addMessages()`, `registerMessages()`
- Any mechanism to replace a compiled message function's return value
- Any hook or plugin system for intercepting message function calls
- Any library distribution pattern with host overrides

## 13. Distinction: Supported Workflow vs. Possible Workarounds

### Officially Supported Workflow

The supported way to share translations from a reusable package is:

1. **Props-based i18n:** The library accepts already-translated strings as props. The host calls `m.*` functions and passes results. The library has zero i18n dependency. [5]
2. **Locale forwarding:** The library compiles its own messages with `baseLocale` strategy, then uses `overwriteGetLocale`/`overwriteSetLocale` to follow the host's locale. The library's messages are its own and cannot be overridden by the host. [5]

### Possible Workarounds (not officially supported)

| Workaround | Mechanism | Viability |
|---|---|---|
| **Compile-time pathPattern merge** | Host adds library messages as a `pathPattern` entry and appends override files after | Host must own compilation; library can't ship precompiled output; not runtime |
| **Build-time file replacement** | Host build tool replaces library's compiled message files before bundling | Fragile, no API, breaks `node_modules` integrity |
| **Wrapper functions** | Library exports wrapper functions that check a runtime override map before falling back to compiled defaults | Adds runtime overhead; loses tree-shaking; custom infrastructure |
| **Dual compilation** | Library compiles with its own `project.inlang` and ships as a pre-built i18n package (Pattern 2 from monorepo docs) | Host imports library messages directly but can't override individual keys |
| **Fork the message files** | Host copies library message files into its own `project.inlang` and edits them | Source forking; PRD explicitly wants to avoid this |

## 14. Assessment Against PRD Requirements

| PRD Requirement | Paraglide JS Capability |
|---|---|
| Package components render built-in text | ✅ Via separate compilation + locale forwarding (Option B) |
| Host passes partial overrides for package messages | ❌ No runtime override API |
| Compute effective messages as `defaults ⋈ overrides` before use | ❌ No message composition API |
| Host override transport must be deterministic | ❌ No transport exists |
| Same global Composer drives host + library locale | ❌ No global Composer; each compilation has independent runtime |
| Partial overrides preserve untranslated sibling defaults | ❌ Not possible — all-or-nothing per message function |
| Package namespaces to avoid collisions | ❌ No namespace mechanism in compiler |
| Repeated mounts don't cause leakage | ✅ Each compilation's runtime is stateless beyond locale |
| SSR/multi-app safety | ✅ Via AsyncLocalStorage + locale forwarding |

## 15. Conclusion

**Paraglide JS cannot satisfy the PRD's core requirement: a library shipping default translations that a host can override at runtime.** The compiler-first architecture makes this fundamentally impossible without Paraglide adding new runtime APIs for message registration and merging.

The closest supported pattern (Option B: separate compilation + locale forwarding) handles locale synchronization but does not allow host message overrides. The message format plugin's `pathPattern` merge is compile-time only and requires the host to own the compilation.

For the PRD's stated architecture (global Vue I18n Composer with precomposed overrides), **Vue I18n remains the appropriate foundation.** Paraglide JS would require a complete redesign of the library i18n contract toward either props-based translation or a shared compilation model that eliminates the library/host boundary.

If Paraglide JS's compiler-first approach is still desirable for other reasons (bundle size, type safety), the library i18n contract would need to shift to one of:
- **Props-based:** Library components accept translated strings as props; no i18n inside the library.
- **Shared catalog:** Library and host share one `project.inlang`; library messages are part of the host's compilation (no independent library distribution).
- **Future API:** Watch for a potential runtime message registration API in Paraglide JS (no indication of this in current issues or roadmap).
